# AI-PLAN.md — Работа с ИИ-ассистентом

## Инструмент
ИИ-ассистент в чате (Deepseek). Без интеграции в IDE, без использования GigaCode/GigaIDE.

## Как велась работа
Задачи ставились пошагово: сначала проектирование БД и миграций, затем настройка слоя доступа к данным (JPA), реализация бизнес-логики правил ККД, расчет метрик и API.
По каждому шагу фиксируется, что было предложено ассистентом, что принято как есть, а что переписано вручную с обоснованием причин.

## Постановка задач и результаты

### Шаг 0. Настройка окружения
**Проблема:** При открытии проекта в IntelliJ IDEA весь код Spring подсвечивался красным, при синхронизации Maven вылетала ошибка `Unable to create injector... Guice/MissingImplementation`.

**Решение:** Выяснилось, что системный Maven не установлен. При этом Spring Initializr сгенерировал Maven Wrapper (`./mvnw`), который работал корректно (версия 3.10.0, Java 21).

**Действие:** В настройках IDEA переключила Maven home path на `Use Maven wrapper` и выполнила Reload. Проблема решена. Позже проект был перегенерирован на Spring Boot 3.5.x (требование ТЗ — Spring Boot 3).

### Шаг 1. Схема БД и миграции
**Задача ассистенту:** написать `docker-compose.yml` для PostgreSQL, настроить `application.yml` и сгенерировать Liquibase changelog (с rollback) для таблиц `unit`, `goal`, `key_result`, `kkd_rule`, `kkd_run`, `kkd_issue`.

**Принято как есть:**
- структура `docker-compose.yml` и настройки `application.yml`
- синтаксис Liquibase changelog с rollback для всех таблиц
- структура таблиц и внешних ключей

**Переписано вручную:**
- поменяла порты для PostgreSQL на 5455, так как другие порты на моем локальном устройстве были заняты.

### Шаг 2. Настройка миграций и тестовых данных
**Задача ассистенту:** расширить файл миграций `002-insert-data.xml` до 24 целей (в соответствии с требованием ТЗ "20-30 целей"), распределив их по 3 подразделениям с иерархией. Обеспечить наличие нарушений по всем 4 правилам и данных для расчета дельты между прогонами (new / persisting / resolved).

**Принято как есть:**
- структура и объем данных (24 цели, KR, 2 прогона, справочник правил)
- маппинг ID для целей и KR

**Переписано вручную:**
- добавила английские комментарии в XML-файл (для соответствия стандартам кода)

### Шаг 3. Слой доступа к данным (JPA Entities)
**Задача ассистенту:** сгенерировать JPA-сущности (`Unit`, `Goal`, `KeyResult`) для маппинга на существующие таблицы PostgreSQL, а также интерфейсы репозиториев для доступа к данным.

**Принято как есть:**
- маппинг полей и связей (`@ManyToOne`, `@JoinColumn`)
- использование `UUID` для идентификаторов целей и KR
- типы `BigDecimal` для весов и значений
- интерфейсы репозиториев с нужными методами поиска

### Шаг 4. Бизнес-логика правил (Rule Engine)
**Задача ассистенту:** реализовать изолированный слой бизнес-логики для проверки данных. Создать интерфейс `KkdRule`, DTO `FoundIssue` для возврата найденных проблем, контекст `KkdContext` для загрузки данных, 4 реализации правил (`GoalNoOwnerRule`, `KrWeightsSumRule`, `CascadeNoParentRule`, `KrStaleProgressRule`) и `RuleEngine` для их совместного запуска.

**Принято как есть:**
- интерфейс `KkdRule` и структура `FoundIssue`
- логика всех 4 правил
- `RuleEngine` с загрузкой данных одним запросом (без N+1)
- использование Java Stream API для фильтрации данных

**Переписано вручную:**
- в настройках IDEA включила `Annotation Processing` для корректного отображения Lombok-аннотаций (иначе IDE не видела сгенерированные геттеры)

**Причина правок:** техническая необходимость для комфортной работы в IDE.

### Шаг 5. Слой хранения результатов ККД
**Задача ассистенту:** создать JPA-сущности для таблиц `kkd_run`, `kkd_rule` и `kkd_issue` (чтобы сохранять результаты прогонов), а также интерфейсы репозиториев для доступа к ним.

**Принято как есть:**
- маппинг полей и связей (`@ManyToOne` на прогон и правило)
- структура репозиториев

**Переписано вручную:**
- переименовала сущность для таблицы `kkd_rule` в `KkdRuleEntity`, чтобы избежать конфликта имен с интерфейсом `KkdRule` из пакета `rule`.

**Причина правок:** избежание путаницы в коде (интерфейс правила и сущность справочника правил не должны называться одинаково).

### Шаг 6. Сервис и API для запуска прогона
**Задача ассистенту:** написать `KkdRunService` (запускает правила и сохраняет результаты в БД) и `KkdRunController` (POST `/api/runs` для ручного запуска).

**Принято как есть:**
- логика `executeNewRun()` (генерация ID, сохранение прогона и проблем)
- структура контроллера

**Проверено:** POST-запрос на `/api/runs` в Postman успешно создает новый прогон и возвращает JSON (например, `RUN-8D36A770`).
